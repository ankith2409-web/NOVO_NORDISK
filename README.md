# Concordance

**Novo Nordisk GBS Hackathon 2026 — Problem Statement 5**
An AI agent with a chatbot interface that automates BRD/FRD creation, extracts Power BI
semantic layer details, and documents tables, joins, KPIs, measures and DAX logic.

Team lead: HB Mrudhal Ankith · Faculty: Dr. R Ruhin Kouser, Dr. Shambhavi

---

## The idea

Requirements documents and the models they describe drift apart the moment someone edits a
measure, and nothing notices. Concordance binds each requirement to the implementation object that
satisfies it using a **fingerprint of the normalised DAX**, so documentation becomes something a
machine can check rather than prose that quietly goes stale.

It runs in both directions: forward from requirements to implementation, and backward —
reconstructing the BRD an existing `.pbix` implies, which is where most real reports start,
since the original document is usually long gone.

### Knowing what was *not* extracted

A graph missing a model's KPIs looks exactly like a graph from a model that has none, and
documentation generated from it would be confidently wrong. So every extraction reports which
features it saw but did not turn into graph objects:

```
Coverage: no unextracted model features detected.
```

PBIXRay also surfaces KPI objects, row-level security, object-level security, calculation
groups and perspectives. All three sample models contain **zero rows and no column schema** for
every one of these, so their layout cannot be learned from the data available — writing
extraction code against a guessed schema would be precisely the confident-but-wrong work this
project exists to prevent. They are counted and reported instead, so a model that *does* use
them produces a visible gap rather than a silently incomplete graph.

## Quick start

```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"

.venv/bin/python -m concordance.cli inspect data/models/Sales_Returns_Sample.pbix
.venv/bin/python -m pytest tests/ -q
```

### Sample models

The three `.pbix` files are Microsoft's publicly distributed Power BI samples and are **not
committed** — together they are ~16 MB of binaries, which does not belong in git. Place them in
`data/models/` using these exact names:

```
data/models/Sales_Returns_Sample.pbix
data/models/AdventureWorks_Sales.pbix
data/models/Supply_Chain_Sample.pbix
```

Tests that need a model call `pytest.skip` when it is absent, so the suite still runs on a fresh
clone — it just covers less. The DAX canonicaliser tests (the ones that matter most) need no
model at all and always run.

## Commands

```bash
concordance inspect  <model.pbix>            # tables, joins, measures, unresolved references
concordance extract  <model.pbix> [-o path]  # write the semantic graph as JSON
concordance explain  <model.pbix> <measure>  # expression, canonical form, dependencies, impact
concordance verify   <model.pbix> <measure>  # prove the fingerprint on real model content
```

`explain` resolves dependencies transitively:

```
$ concordance explain data/models/Sales_Returns_Sample.pbix "Last 2 Months Net Sales"

expression  : [Net Sales]+[Net Sales PM]
depends on (5):
  column:Calendar[Date]
  column:Sales[Amount]
  column:Sales[Status]
  measure:Analysis DAX[Net Sales PM]
  measure:Analysis DAX[Net Sales]
```

## How the fingerprint works

An expression is lexed, stripped of comments and formatting, case-folded on object names
(DAX object names are case-insensitive), normalised on table-qualifier quoting and numeric
literals, then hashed. String literals are preserved byte for byte, because `"Sold"` and
`"sold"` are different filter values and must never collapse onto the same fingerprint.

```
CALCULATE(SUM(Sales[Amount]),Sales[Status]="Sold")          -> 2256ab42c5af
CALCULATE (                       // reformatted, requalified, recased
    SUM ( 'Sales'[Amount] ),
    'Sales'[status] = "Sold" )                              -> 2256ab42c5af   same
CALCULATE(SUM(Sales[Amount]),Sales[Status]="Returned")      -> 527f2635eb86   drift
```

This is a lexer rather than a set of regexes for a concrete reason: a `//` or `--` inside a
string literal is not a comment, and treating it as one silently corrupts the expression.

## Layout

```
concordance/
  normalize/dax.py     DAX lexer and canonicaliser — the fingerprint depends on this
  fingerprint.py       SHA-256 over canonical form
  model.py             platform-independent object model
  adapters/
    base.py            the contract a source platform implements
    pbix.py            Power BI, via PBIXRay (MIT)
  graph/csg.py         the Canonical Semantic Graph
  cli.py
tests/                 76 tests, run against the real .pbix files
data/models/           three Microsoft sample models
```

## Notes from building the extractor

Three defects surfaced only by running against real models rather than synthetic fixtures.
All three are pinned by regression tests in `tests/test_reference_resolution.py`.

- **Qualified measure references.** `'% Return Rate'[% Return Rate Value]` is a measure, not a
  column. Assuming `Table[Name]` is always a column lost the dependency edge and reported a
  phantom missing column.
- **Measure-only tables.** PBIXRay lists only tables that store data, so `Analysis DAX` and
  `Design DAX` — holding 58 measures between them — never appeared. The graph grew
  attribute-less placeholder nodes where those tables should have been.
- **Date-hierarchy syntax.** In `'Calendar'[Date].[Month]`, the `[Month]` is a level on
  `Calendar[Date]`, not an object of its own. The level still changes the fingerprint, so it is
  kept in the canonical form and skipped only during dependency extraction.

**Hierarchies were missing entirely.** Found by auditing what PBIXRay exposes against what the
adapter actually read — no test failed, because no test knew to look. Every hierarchy in every
model was invisible: `Product[Products]` (Category → Subcategory → Model → Product) and five
other business drill paths in AdventureWorks. They are semantic-layer content a BRD has to
describe, and impact analysis was blind to them, so changing a column could break a drill path
with nothing reporting it. Now extracted, level order preserved (order is meaning — Year → Month
is not Month → Year, and the fingerprint reflects that), each level bound to the column that
supplies it.

A further defect surfaced in a post-push audit rather than from a failing test — worth
naming differently because it was found by reasoning about the code, not by a model exposing it.
`row.get("Expression") or ""` looks like a safe default; it isn't, because a pandas NaN is truthy
in Python, so a genuinely missing expression would silently become the literal string `"nan"` and
get fingerprinted as if it were real DAX. None of the three sample models happen to have a measure
with a missing expression — pinned in `tests/test_nan_handling.py` with a synthetic row rather
than waiting for a file that triggers it.
