# Concordance

**Novo Nordisk GBS Hackathon 2026 — Problem Statement 5**
An AI agent with a chatbot interface that automates BRD/FRD creation, extracts Power BI
semantic layer details, and documents tables, joins, KPIs, measures and DAX logic.

Team lead: HB Mrudhal Ankith · Faculty: Dr. R Ruhin Kouser, Dr. Shambhavi

---

## The idea

Requirements documents and the models they describe drift apart the moment someone edits a
measure, and nothing notices. Concordance binds each requirement to the implementation object that
satisfies it using a **fingerprint of the normalised DAX**, so documentation becomes something a
machine can check rather than prose that quietly goes stale.

It runs in both directions: forward from requirements to implementation, and backward —
reconstructing the BRD an existing `.pbix` implies, which is where most real reports start,
since the original document is usually long gone.

## Status

**Week 2 complete** — BRD/FRD generation, and a chatbot over the model in terminal and browser.
**Week 3 in progress** — drift detection works, and the warehouse connector reconciles the
same KPI across Power BI and SQL.

Requirements are *derived* from the graph by deterministic code, never generated by a
language model. The model's only jobs are choosing which tool to call and phrasing what
that tool returned. Every number below comes from the real models in `data/models/`.

therefore cannot be resolved from a `.pbix` at all.

### Knowing what was *not* extracted

A graph missing a model's KPIs looks exactly like a graph from a model that has none, and
documentation generated from it would be confidently wrong. So every extraction reports which
features it saw but did not turn into graph objects:

```
Coverage: no unextracted model features detected.
```

PBIXRay also surfaces KPI objects, row-level security, object-level security, calculation
groups and perspectives. All three `.pbix` samples contain **zero rows and no column schema** for
every one of these, so their layout cannot be learned from the data available — writing
extraction code against a guessed schema would be precisely the confident-but-wrong work this
project exists to prevent. They are counted and reported instead, so a model that *does* use
them produces a visible gap rather than a silently incomplete graph.

```bash
python3 -m venv .venv

```

### Sample models

The three `.pbix` files are Microsoft's publicly distributed Power BI samples and are **not
committed** — together they are ~16 MB of binaries, which does not belong in git. Place them in
`data/models/` using these exact names:

```
data/models/Sales_Returns_Sample.pbix
data/models/AdventureWorks_Sales.pbix
data/models/Supply_Chain_Sample.pbix
```

The fourth model, `ClinicalTrialSafety.SemanticModel/`, **is** committed: TMDL is text, and it
is our own work rather than a redistributed sample. It models clinical trial operations and
post-marketing safety — MedDRA term hierarchy, CTCAE severity, investigator causality
assessment, WHO ATC codes, PRR signal detection. Its structure mirrors real pharmacovigilance
reporting; its contents are synthetic and labelled as such in the model description.

Tests that need a model call `pytest.skip` when it is absent, so the suite still runs on a fresh
clone — it just covers less. The DAX canonicaliser tests (the ones that matter most) need no
model at all and always run.

## Commands

Every command takes either a `.pbix` file or a TMDL model folder; the adapter is chosen
from the path.

```bash
concordance inspect  <model>            # tables, joins, hierarchies, measures, coverage
concordance extract  <model> [-o path]  # write the semantic graph as JSON
concordance explain  <model> <measure>  # expression, canonical form, dependencies, impact
concordance verify   <model> <measure>  # prove the fingerprint on real model content
concordance document <model> --type brd # generate a BRD (--type frd, --format docx)
concordance auditpack <model>            # evidence bundle: docs + fingerprint manifest
concordance ask      <model> "question"  # ask about the model (omit for interactive)
concordance serve    <model> [--port]    # web UI + JSON API at http://127.0.0.1:8000
concordance snapshot <model> --label v1  # record fingerprints for later comparison
concordance drift    <before> <after>    # what changed, and which requirements are affected
concordance reconcile <model> [--warehouse db]  # compare KPIs against a SQL warehouse
```

`explain` resolves dependencies transitively:

```
$ concordance explain data/models/Sales_Returns_Sample.pbix "Last 2 Months Net Sales"

expression  : [Net Sales]+[Net Sales PM]
depends on (5):
  column:Calendar[Date]
  column:Sales[Amount]
  column:Sales[Status]
  measure:Analysis DAX[Net Sales PM]
  measure:Analysis DAX[Net Sales]
```

## The JSON API

`serve` exposes eleven read-only endpoints alongside the chat, so a front end can
reach everything the CLI can. They are plain functions in `web/api.py` — the HTTP
handler only routes, sets headers and manages the chat session — so each one is
tested without opening a socket.

```bash
concordance serve data/models/ClinicalTrialSafety_v2.SemanticModel \
  --compare-to data/models/ClinicalTrialSafety.SemanticModel \
  --warehouse  data/warehouse/quality_control.duckdb
```

| Endpoint | Answers |
|---|---|
| `GET /api/overview` | counts, coverage gaps, and which of the below are configured |
| `GET /api/graph` | the whole semantic graph, nodes and edges |
| `GET /api/tables` · `/api/table?name=` | tables, and one table in full |
| `GET /api/measures` · `/api/measure?name=` | measures, and one with its canonical form and fingerprint |
| `GET /api/impact?name=` | what would be affected if this object changed |
| `GET /api/requirements?kind=business\|functional` | generated requirements, each bound to its evidence |
| `GET /api/review` | only what the system is not confident about |
| `GET /api/drift` | what moved against the configured comparison model |
| `GET /api/reconcile` | whether the configured warehouse agrees, metric by metric |
| `POST /api/ask` | the grounded chat — the one endpoint with session state |

### The client never names a file

Drift needs a second model and reconciliation needs a warehouse. The obvious way
to supply them — a query parameter holding a path — would turn a read-only local
server into an arbitrary file reader. Both are instead configured at launch, so a
request can only ask *whether* to compare, never *what against*. Endpoints that
were not configured answer `501` naming the flag that would enable them, rather
than pretending the feature does not exist.

### Cross-origin requests are limited to loopback

A front-end dev server runs on its own port, so its calls are cross-origin. Only
`localhost`, `127.0.0.1` and `[::1]` are allowed, and the origin is echoed rather
than answered with `*` — the session cookie makes these credentialed requests,
where the wildcard is invalid anyway. Any other origin gets no allow header at
all: this API serves a local model and, through the chat, spends real API quota,
so a page the user merely happens to have open must not be able to read it.

### Reads do not create sessions

Only `/api/ask` accumulates history, so only it gets a session. The graph is built
once and never mutated, so every reader shares it — which also means a page that
loads six panels does not evict six real conversations from the session store.

## The interface

A React app over the JSON API. It is a separate process from the Python server on
purpose: the API is needed by any front end, so that work is never wasted, and a
build problem in the interface cannot take the backend down with it.

```bash
concordance serve data/models/QualityControl.SemanticModel \
  --warehouse data/warehouse/quality_control.duckdb   # API on :8000

cd frontend && npm install && npm run dev             # interface on :5173
```

The dev server proxies `/api` to the Python process, so the browser stays on one
origin and the chat's session cookie behaves exactly as it will in production.
The server's cross-origin support is what allows the two to be served from
different ports, but developing through it would mean testing a path the shipped
app never takes.

Six views: **Overview** (counts and what could not be read), **Model** (tree,
definition, fingerprint chain, impact), **Requirements** (BRD/FRD with evidence
per row), **Drift**, **Reconcile**, and **Review**. Drift and Reconcile appear
only when the server was started with something to compare against.

### Sharing it without a server

The interface normally talks to a running `concordance serve`. There is a second
build that answers from a captured run instead, inlined into a single HTML file
that needs no backend — for a reviewer, or anyone without the repo:

```bash
python scripts/capture_snapshot.py     # against a running server
cd frontend && npm run build:snapshot  # one self-contained dist/index.html
```

Everything it shows came from a real extraction, and it says on screen that it is
a snapshot. The mode is chosen at build time, never as a fallback when a request
fails: a silent fallback would hide a dead server behind stale data, which is the
confidently-wrong behaviour this project exists to avoid. The ordinary build
contains no capture at all and still says plainly when it cannot reach the API.
The chat is absent from a capture by nature — it answers by calling tools against
a live graph, so there is nothing to record.

### What the design is trying to do

Every comparable tool shows conclusions. The point of this one is that it shows
why it believes them, so three things the backend already computes are given more
weight than they usually get:

- **Coverage gaps lead.** The overview opens with what could not be read or
  resolved, above the counts. When there is nothing to declare it says so — a
  blank space is indistinguishable from not having checked.
- **Confidence is never hidden.** A low-confidence statement is inferred from
  structure alone, and is chipped as such rather than rendered in the same weight
  as something the model states outright.
- **A state is never colour alone.** Every verdict and confidence chip carries
  its word. Audit packs get printed in monochrome, projectors flatten a muted
  palette, and roughly one in twelve men has some colour vision deficiency.

Semantic colour is reserved for the three-state verdict — consistent, review,
divergent — and the same triple carries requirement confidence. The product's own
accent is a separate hue and is never used to mean anything.

## Asking questions about a model

`ask` answers from the model rather than from training. Every answer is produced by
calling read-only tools over the graph, so a language model that has never seen your
`.pbix` still describes it correctly — and cannot describe what is not there.

```
$ concordance ask data/models/ClinicalTrialSafety.SemanticModel \
    "How is Serious Adverse Events calculated, and what would break if I changed it?"

DAX Expression:
  CALCULATE([Adverse Event Count], AdverseEvent[Seriousness] = "Serious")

Depends on: [Adverse Event Count], AdverseEvent[Seriousness]
If changed, affected: [SAE Rate per 100 Patients]
```

Asked for a measure that does not exist, it says so instead of inventing one:

```
$ concordance ask <model> "What is the DAX for the 'Patient Mortality Index' measure?"

There is no measure named 'Patient Mortality Index' in the semantic model.
The closest matching measure is Patients Enrolled.
```

`--show-tools` prints which tools produced an answer, and flags any answer that reached
the user without consulting the model at all.

### Two things the loop guards against

**Invented tools.** Given a question its declared tools did not fit, Gemini called a
`list_measures` function that had never been offered. Every call is checked against the
registry; an unknown name is answered with an error the model can recover from, rather
than dispatched or silently dropped.

**Runaway loops.** Tool rounds are bounded. On reaching the limit the loop asks once more
without tools, so the user gets an answer rather than silence.

Provider setup: put `GEMINI_API_KEY=...` in a `.env` file at the project root (gitignored).
The model sits behind a provider interface, so swapping it is configuration, and tests run
against a scripted fake with no network or key.

### Web interface

`serve` runs the same agent behind a local browser page — the problem statement's "chatbot
interface" as something a judge can actually click into, not a terminal command.

```bash
concordance serve data/models/ClinicalTrialSafety.SemanticModel
# -> http://127.0.0.1:8000/
```

Deliberately dependency-free: the whole web layer is Python's standard library
(`http.server`, `json`), consistent with the Gemini provider avoiding an SDK. Each browser
tab gets its own conversation via a session cookie — two judges opening the page at once do
not share or corrupt each other's chat history. The page itself renders the model's Markdown
(bold, code fences, bullets) and shows which tools produced each answer, so the grounding is
visible, not just claimed.

## How requirements are derived

`document` reads the graph and writes the requirements it implies — the reverse of the usual
direction, since most real reports have no surviving BRD.

Nothing is invented. Every requirement comes from a node that exists and carries the node id
and fingerprint it was derived from, so a language model can later rephrase a requirement but
cannot add one. Requirement ids come from an object's *identity* (its table and name), never
from its expression, so editing a measure keeps its requirement id stable and drift is reported
against it rather than silently retiring one requirement and minting another.

Confidence is earned rather than asserted:

| | Meaning | Example |
|---|---|---|
| **high** | The model states it | What a measure computes |
| **medium** | Follows from a structural rule | A join enables analysis — but the model never says *why* it exists |
| **low** | Genuinely inferred, or undefined | An inactive relationship's purpose; an object declared with no definition |

Low-confidence requirements are routed to a review queue printed at the top of the document,
and never presented as settled. In the clinical model that is two items, both inactive
relationships — because nothing in a Power BI model ever records why an inactive relationship
exists.

Objects the model declares but leaves undefined — a measure with no expression, a hierarchy
with no levels — are reported as incomplete rather than specified. A document that confidently
describes something which does not exist is the failure this project is built to prevent.

## Word output and the evidence pack

`--format docx` writes a real Word document — built-in heading styles so Word's navigation
pane works, DAX in monospace, and the traceability matrix as a proper table. The people who
sign a BRD open it in Word and comment in the margin; the hackathon's own rules require
Office 365 "for the exchange of material", which is a fair signal of how these documents
travel.

`auditpack` answers the question a validation reviewer actually asks — *how do you know this
document is correct?*

```bash
concordance auditpack data/models/ClinicalTrialSafety.SemanticModel
```

```
  80 requirements, 102 fingerprinted objects
  2 awaiting human confirmation

    ClinicalTrialSafety.BRD.docx     ClinicalTrialSafety.BRD.md
    ClinicalTrialSafety.FRD.docx     ClinicalTrialSafety.FRD.md
    ClinicalTrialSafety.fingerprints.json
    MANIFEST.json                    README.txt
```

The fingerprint manifest is what makes the pack *checkable* rather than merely produced:
anyone holding the pack and the model can re-run `concordance drift` against it and see
whether anything has moved since. The manifest also records what could **not** be read —
unresolved references and unextracted feature types — because a pack that hid its own gaps
would misrepresent how complete it is.

It records what was extracted and what each requirement was bound to. Whether that satisfies
any particular regulatory expectation is a judgement for the organisation's quality function,
and the pack's README says so rather than implying otherwise.

## Reconciling a KPI across platforms

The same KPI usually exists twice: once as a DAX measure, once as a warehouse view built
by a different team. When the two definitions drift apart nobody finds out until two
reports disagree in a meeting.

```bash
python scripts/build_warehouse.py          # builds the local DuckDB fixture
concordance reconcile data/models/QualityControl.SemanticModel
```

```
Cross-platform KPI reconciliation
====================================================================
  6 metric(s) defined on more than one platform: 1 divergent, 1 need review, 4 consistent

Divergent - these will report different numbers (1)
--------------------------------------------------------------------
  OOS Rate
      [power_bi/dax] DIVIDE([OOS Results], [Tests Performed], 0)
          via OOS Results, Tests Performed
      [warehouse/sql] CREATE VIEW oos_rate AS SELECT (CAST(count_star() FILTER (WHERE ...
      ! source tables: power_bi reads ['testresult']; warehouse reads ['batch', 'testresult']

Needs review - differs, but may still agree (1)
--------------------------------------------------------------------
  Batch Yield %
      [power_bi/dax] DIVIDE(SUM(Batch[ActualYield]), SUM(Batch[TheoreticalYield]), BLANK())
      [warehouse/sql] CREATE VIEW batch_yield_pct AS SELECT avg((CAST(b.actual_yield AS ...
      ! aggregation: power_bi applies ['SUM']; warehouse applies ['AVG']
```

Both findings are real. `oos_rate` divides by batches where the measure divides by tests.
`batch_yield_pct` averages per-batch ratios where the measure takes the ratio of sums.
The other four implementations of the same metrics are faithful, and are reported as
consistent — a checker that flags everything is no more useful than one that flags nothing.

### Why this cannot work by fingerprint

Fingerprints prove a definition has not changed *in the same language*. DAX and SQL never
hash alike even when they compute the same number, so equal fingerprints are impossible
here and unequal ones prove nothing. The comparison instead works on what each definition
structurally does — which tables it reads, which columns, which aggregations.

That is evidence, not proof. Deciding whether two arbitrary expressions in two languages
compute the same number is undecidable in general. So the report has three verdicts, and
the middle one exists because it is honest: **divergent** when the two read different data,
**needs review** when they differ in a way that might still agree, **consistent** when
nothing distinguishes them. Only divergence fails a pipeline under `--fail-on-conflict`;
an unresolved question is not a defect.

### Composed measures are resolved first

`OOS Rate` is `DIVIDE([OOS Results], [Tests Performed], 0)`. It names no table and no
column, so compared as written it appears to read nothing — and would be flagged against
*any* warehouse implementation, including a correct one. What it really reads is whatever
the measures it calls read, so those are folded in first and the report says which ones it
went through. The same is done for a view selecting from another view.

### Names are matched, and near misses are offered rather than assumed

A warehouse view is `oos_rate` where the measure is `OOS Rate`, so matching ignores case
and separators, and expands the symbols SQL will not accept in an identifier (`Batch
Yield %` matches `batch_yield_pct`). Beyond that the report stops guessing: unmatched names
that merely *resemble* each other are listed for a person to confirm, never compared.
No character measure can tell that `Batches Released` and `batches_rejected` — which score
0.80 similar — mean opposite things.

### What is genuinely tested, and what is not

The SQL path runs end to end against DuckDB, whose `information_schema` follows the same
standard Snowflake and Databricks implement, so the queries, the parsing and the
comparison are really exercised. **Authenticating to a live Snowflake or Databricks account
is not tested**, because this project has no credentials for either; those connectors swap
the DB-API connection and reuse everything above it. The distinction is stated here rather
than left for someone to discover.

## Detecting drift

`drift` compares two versions of a model and reports not just what changed, but **which
requirements are now in question** — the payoff of binding each requirement to a fingerprint.

Both arguments may be a stored snapshot or a live model:

```bash
concordance drift data/models/ClinicalTrialSafety.SemanticModel \
                  data/models/ClinicalTrialSafety_v2.SemanticModel --allow-different-models
```

The repository carries a genuine second version of the clinical model — TMDL is text, so v2 is
an authored edit that `git diff` shows, not a simulated change. Comparing them:

```
  4 changed, 1 added, 1 removed, 97 unchanged

Changed (4)
  measure   Clinical Metrics[Serious Adverse Events]
      before: CALCULATE([Adverse Event Count], AdverseEvent[Seriousness] = "Serious")
      after:  CALCULATE( [Adverse Event Count], AdverseEvent[Seriousness] = "Serious", Adve…
      d551fa5e0b52 -> 8a280045a7fe
  relationship  AdverseEvent[StudyID]->Study[StudyID]
      before: M:1 Single inactive
      after:  M:1 Single active

Requirements now in question (8)
  REQ-F-ab8582  Clinical Metrics[Serious Adverse Events] shall be implemented exactly as…
      via changed measure Clinical Metrics[Serious Adverse Events]
```

### What the report deliberately stays silent about

v2 also reformats `Protocol Deviations` — adds a comment, respaces the call — without touching
its meaning. It does **not** appear in the report. That silence is the feature: a drift report
that fires on whitespace is one nobody reads, so it is asserted in the tests as firmly as the
changes are.

### Why the requirement ids hold still

`REQ-F-ab8582` names the same requirement in both versions while its bound fingerprint moves
from `d551fa5e0b52` to `8a280045a7fe`. Requirement ids come from an object's identity, not its
content — had they been derived from the expression, editing a measure would retire one
requirement and mint another, and nothing would be reportable as *drifted* at all.

`--fail-on-drift` exits non-zero, so this can gate a deployment pipeline.

## How the fingerprint works

An expression is lexed, stripped of comments and formatting, case-folded on object names
(DAX object names are case-insensitive), normalised on table-qualifier quoting and numeric
literals, then hashed. String literals are preserved byte for byte, because `"Sold"` and
`"sold"` are different filter values and must never collapse onto the same fingerprint.

```
CALCULATE(SUM(Sales[Amount]),Sales[Status]="Sold")          -> 2256ab42c5af
CALCULATE (                       // reformatted, requalified, recased
    SUM ( 'Sales'[Amount] ),
    'Sales'[status] = "Sold" )                              -> 2256ab42c5af   same
CALCULATE(SUM(Sales[Amount]),Sales[Status]="Returned")      -> 527f2635eb86   drift
```

This is a lexer rather than a set of regexes for a concrete reason: a `//` or `--` inside a
string literal is not a comment, and treating it as one silently corrupts the expression.

## Notes from building the extractor

Three defects surfaced only by running against real models rather than synthetic fixtures.
All three are pinned by regression tests in `tests/test_reference_resolution.py`.

- **Qualified measure references.** `'% Return Rate'[% Return Rate Value]` is a measure, not a
  column. Assuming `Table[Name]` is always a column lost the dependency edge and reported a
  phantom missing column.
- **Measure-only tables.** PBIXRay lists only tables that store data, so `Analysis DAX` and
  `Design DAX` — holding 58 measures between them — never appeared. The graph grew
  attribute-less placeholder nodes where those tables should have been.
- **Date-hierarchy syntax.** In `'Calendar'[Date].[Month]`, the `[Month]` is a level on
  `Calendar[Date]`, not an object of its own. The level still changes the fingerprint, so it is
  kept in the canonical form and skipped only during dependency extraction.

**Hierarchies were missing entirely.** Found by auditing what PBIXRay exposes against what the
adapter actually read — no test failed, because no test knew to look. Every hierarchy in every
model was invisible: `Product[Products]` (Category → Subcategory → Model → Product) and five
other business drill paths in AdventureWorks. They are semantic-layer content a BRD has to
describe, and impact analysis was blind to them, so changing a column could break a drill path
with nothing reporting it. Now extracted, level order preserved (order is meaning — Year → Month
is not Month → Year, and the fingerprint reflects that), each level bound to the column that
supplies it.

A further defect surfaced in a post-push audit rather than from a failing test — worth
naming differently because it was found by reasoning about the code, not by a model exposing it.
`row.get("Expression") or ""` looks like a safe default; it isn't, because a pandas NaN is truthy
in Python, so a genuinely missing expression would silently become the literal string `"nan"` and
get fingerprinted as if it were real DAX. None of the three sample models happen to have a measure
with a missing expression — pinned in `tests/test_nan_handling.py` with a synthetic row rather
than waiting for a file that triggers it.
